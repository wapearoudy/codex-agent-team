# 0.29.1 能力与边界

## 0.29.0 执行成本与阶段交接

模型入口只传一份 structuredContent 正文，文本通道返回短回执；schema 以版本化 SHA-256 指纹校验显式缓存。dispatch 提供成员常用参数形状，未知输入才 describe。消息回执不重复原文，consume_team_inbox 一次读取并确认确切收件轮次，普通进度仅保存在面板；超大历史消息按页读取后单独确认。

read_team_source 默认4000字符、最多6000字符；prepare_team_command 准备日志路径与1200 token 输出上限，原生工具负责执行和真实退出码。read_team_command_log 默认2000字符，完整日志保存在本地。助手不执行模型，也不冒充 PASS；直接原生命令仍需调用方遵守预算。

wait_team_event 同时监听保存控制与原生终态，普通检查点/日志/用量变化在等待内合并，面板继续刷新。变化回执附紧凑协调状态，终态附准确 attempt IDs，不再重复读团队；超时只再次等待。宿主最长55秒的有界等待仍有模型返回成本，不能静默唤醒已结束的 Leader。

长任务在成员明确提交 handoff 检查点并结束原生轮次后，插件验证 exact completed + 公共回执，续接同一 task 的新干净上下文。完整阶段链、输入指纹与宿主命令保留。每任务最多3次，不占失败重试额度；未知/连接失败不轮换。仅原生成功命令且声明输入指纹未变可复用，最终提交指纹包含复用输入；输入变化即失效。阶段不是验收，仍需独立审核与插件质量门禁。显式合同修订保留前阶段，禁止旧合同验证复用。

## 0.22.0 协调成本与用量覆盖

Leader 的 coordination 视图只返回当前动作、控制、轮次身份、收件提示和预算；cursor 忽略公开日志、时间与非门槛用量跳动，未变化回包只要求继续等待。保存 revision、停止、终态、任务轮次或新消息仍更新 cursor。协调回包上限约6KB；概要不能代替原始验收证据。wait_team_event 超时不要求重复 read_team/inbox，原生等待后可用零时长、observeNative=false 检查保存控制。仍是有界等待，每次工具返回会继续一次模型轮次，不宣称等待完全零 token。

read_team_context 的 evidence 视图按 task/attempt 和 section 读取公开交付、命令列表、单条完整命令与输出；默认4000字符，最多8000。后续页绑定内容 cursor，任务合同、原生轮次或结果变化时拒绝混用，其他任务的 revision 不强迫重读稳定证据。原始记录和质量门禁完整保留。派发提示要求约2000 token 的工具结果、聚焦源码范围和成功日志摘要；宿主命令工具本身的输出上限仍由 agent 参数遵守。

计量以团队 createdAt 到最终验收、归档或替换的时间范围为界，覆盖 Leader 和父级/项目已核实的直接子会话；同线程只计一次，不与 attempt 分项重复相加。新增直接原生兜底会话按创建时间保守归入成本，不能据此推断执行权限、成员/任务关联或验收。旧会话、其他项目或其他父级不读取其公开内容；不解密协作输入，不读取隐藏推理。中断续跑保持原上下文。缺失累计基线、未知用量、计量截断或发现失败均保留不完整标志，不伪称0；展示最多缓存10秒，已配置预算在插件新派发前强制实时核对，超限或严格未知策略不再返回新派发动作/初始化提示。预算不停止已有原生任务，也不直接拦截绕过插件的宿主工具调用。

这些计数包含缓存输入，是处理量，不等于账户账单或额度。按时间推断的兜底归属可能覆盖同一 Leader/项目期间的其他工作，按保守预算列示；间接子代理、未在公开 Leader 活动中出现的会话或已有日志缺失不承诺完整覆盖。页面和统计更新不等于原团队执行状态已正式登记。

宿主文件变更支持数组和按路径索引的对象；解析失败回退游标重读，不跳过剩余记录，身份拒绝在重试中继续拒绝。工程回归、真实 V5 只读统计和本机安装验证不代替原业务团队联合验收。此版本不改变已确认模型或任意设置 token 上限，不中断 V5。

## 数据与执行边界

只观察已核对父会话、项目和成员标记的线程。公开视图不读隐藏推理，不展示派发输入或账号凭据；报告可能含用户主动输出的项目内容。写范围是职责/调度约束，不是操作系统沙箱。

跨 Leader 转移原生句柄、自动重建宿主协作注册表、原生聊天头部/尾卡槽位与原生轮次锚点缺少宿主公开接口。工具返回明确能力边界及原 Leader 入口，不伪造可控状态。插件不为绕过能力限制建立第二个团队或独立执行器。

0.9.0 数据格式使用 `.v2.json` 与不可变分卷；首次写入旧团队保留精确原文备份，并让旧服务拒绝继续写入。迁移失败、卷缺失、身份或校验和冲突均保留数据并拒绝修改。降级服务不能写入已迁移团队。

0.10.0 首次使用合同、问题台账、自动修复或成员生命周期修改时，保留同一数据文件，设置最低版本与 v2 archive manifest（无分卷时也保留空清单）。0.9.x 读取器会在修改前拒绝该清单；旧团队未使用新能力时继续兼容。升级后重启宿主连接；不能通过删保护字段或降级绕过质量门禁。

0.11.0 新建团队启用计划确认记录和最低版本保护；0.10.0 读取器在修改前拒绝此状态。最近 20 个计划版本原文留存，轮询只携带确认状态摘要。语义上的范围扩展依赖 Leader 正确识别；并非自然语言授权判定器。

0.12.0 的自动回归包含初始化中停止、未知预留、选择性重试、合同冻结/回滚、旧版本写入拒绝、成员越权、宿主目录校验、动态模板以及浏览器表单与停止/恢复流程。浏览器检查和本机安装烟测不等同于 Desktop 长时间运行或完整重启验收；原始截图所示渲染进程崩溃尚无本次新版本的现场复现结论。

## 0.13.0 对标状态与统一验收

本轮工程回归覆盖工作流通知并发去重、跨进程/重连保留、未知投递重试、过期通知、计划退回、角色路由、真实模型目录、用户原文与草案的语言切换保护、运行扩岗暂存、模板维护和只读历史切换。自动回归是工程检查，不代替用户要求的最后一次 Desktop 联合验收；本轮没有启动真实业务成员、安装到宿主或宣称已修复现场崩溃。

余下宿主差异：DSH 能在宿主进程内监听成员状态并直接调度/中断，MCP 插件使用 Leader 原生内部工具推进，wait_team_event 监听已保存的面板操作；不运行后台协调模型，也不承诺唤醒没有等待的空闲 Leader。DSH 的既有成员跨 provider/fallback、原生命令/聊天槽位、跨重启句柄恢复依赖不同宿主接口。team_command 只解析真实输入的命令协议，不注册原生斜杠菜单。manage_team(operation=capabilities) 返回当前适配器的明确能力合同，不把读取成功当成控制能力。

运行中合同修改采用先停并核实、再修订的既有约束；这是有意保留的证据一致性要求。双方申报路径检查均不能代替实际 Git 差异审计。不能为了给出“没有差距”的结论，把宿主不支持的控制能力表示为已实现。

使用 routeSnapshot、备用路由或计划退回记录后，最低读取/写入版本为 0.13.0；旧服务拒绝此清单，原备份和校验分卷保留。通知状态单独保存，不通过反复递增业务 revision 制造并发冲突。

## 0.14.0 任务上下文治理

每个已绑定并结算的任务 attempt 之后，下次派发先核实原生成员最新轮次已终止，再保存 contextHistory（岗位、线程、路径、代次、任务、attempt、turn、路由和终态）。新派发使用唯一 taskName 与 fork_turns=none，原生控制仍由同一 Leader 的工具执行；保留同一团队、逻辑岗位与 worktree，不复制旧线程聊天。新绑定不能指向退役线程；若公开记录包含其他任务 attempt，也拒绝当作干净会话。

活动轮次、未知启动结果和未绑定预留不会触发替换；预留重试复用相同 attempt 和会话代次。旧线程不再拥有该岗位的工作权限，不能自领下一项任务。旧交付、消息、检查点、独立审查、历史导航和用量仍绑定真实旧线程。轮换记录使用 0.14.0 最低版本保护与不可变分卷，不丢弃历史。

contextChars 现在统计完整派发提示（固定指令、职责、目标、验收、合同、问题、历史摘要与输出格式），而非只统计交接 JSON。逐步减少可检索的依赖/检查点摘要；要求、验收和质量合同保持原文。若仍超限，原子拒绝整批预留，不能删除要求绕过预算。该字符预算不等于整个模型上下文窗口或精确 token 上限。

任务内的文件读取和工具输出仍会占用上下文，隔离会话也会付出重新读取必要信息的成本；没有承诺零 token 浪费或固定节省比例。工程回归验证会话选择、权限、预算及历史完整性，不代替最终 Desktop 实机验收；未在本轮启动真实业务成员或现场测量节省比例。

## 0.14.1 面板交互

停止/继续位于进度卡内，按真实执行状态显示，不要求用户先填原因；可补充说明且自动记录操作来源。停止请求与已核实停止明确区分，通知失败保留请求并提示回到主会话；确认停止前不提供继续按钮。恢复默认勾选因团队停止中断的任务，显示重试数量，可展开取消或选择失败任务；不会默认重跑失败任务。

## 0.14.2 工作台视觉与任务入口

按目标与进度、成员、任务、依赖的顺序展示工作台。总览突出实际团队状态与对应任务，进度百分比作为辅助信息；执行中来自当前任务对应的公开执行记录，状态未知、停止与待审查分别呈现。成员在足够宽时双列展示，窄屏自动单列，操作入口底部对齐；任务按名称、负责岗位和状态对齐。使用克制的边界、字号和状态颜色区分层级。

任务区的“当前关注”以简短提示依次选取异常、执行中、待审查或已就绪任务；遵循搜索与筛选，暂停时保留暂停措辞，全部完成时隐藏。

任务列表来自真实团队记录，显示任务名称、岗位与状态，搜索和状态筛选与依赖图同步；点击或键盘打开对应任务，关闭详情回到任务入口。超过 100 条会明确提示使用筛选。

依赖图不在悬停或键盘焦点经过时弹出详情；点击节点或按 Enter 才选择任务并显示依赖链，Escape 或再次点击取消选择。

界面岗位显示简短名称，重复岗位以 ID 区分；原生完整名称仍保留在提示和执行证据中，身份绑定与导航协议不变。运行说明和用量在下方展开，工作区准备阻塞与验证限制主动展开，不会被常规说明的折叠隐藏。明暗模式、窄屏、真实历史导航和 400 次大型记录刷新继续回归；Desktop 联合验收待执行。

## 0.14.3 验证命令与历史交付

识别标准 sh/bash/zsh 的 -c / -lc / -cl 及登录参数包装，单引号、双引号和字面量转义只用于解出完整脚本；脚本仍按完整原文核对。外层展开、额外参数、追加命令、重定向或未知 shell 不解包，不用子串匹配。成功证据仍必须来自本轮宿主命令的 completed + exitCode 0；原始合同与宿主命令保留，并记录匹配来源。

显式 accept_team_review 和 finish_team 从当前 attempt 保存的 observation.commands 重新计算验证结果，旧缓存误判可以随正常验收事务更新，不重派、不重复 settle、不自动接受审查。缺失宿主原始证据、失败命令、未完成检查或缺少独立审查仍拒绝验收；只读读取不改团队状态。受控升级回归覆盖旧误判恢复与缓存成功不能替代真实证据，业务团队由原 Leader 在加载新版后继续验收。

0.20.0 对照 DSH 的共享快照、单一轮询和断线保留成功状态，补齐面板的执行样本合并：业务 revision 与原生观察时间分别判断；相同 attempt/turn 的终态不回退，较晚的旧控制回执不覆盖较新的执行观察，合法续跑依原关联链更新。每秒状态同步，同一成员并发观察合并；当前交付仍需原 Leader 接收和独立验收。已完成团队的 workflow 无后续动作，原接收/审查/最终验收重复参数只返回已有结果。wait_team_event 用文件事件监听已登记原生成员，事件合并、核对限频；只在已验证终态上返回 member-terminal，不在每条公开进度上唤醒模型，也不启动后台协调器。已结束的 Leader 仍不承诺自动唤醒；技能要求派发后保持当前工作轮次直到完成或明确停止。

### 0.30.0 历史验证关联

保存宿主 commandId/cwd；命令完整内容与工作目录匹配。补登记只读取当前已提交 work 的同 attempt 原生连续轮次，要求终态 completed/exitCode=0、原候选指纹不变，历史轮次额外绑定原报告内的输入哈希表、原声明 SHA256 manifest 或准备命令的预执行指纹。完整文件与目录闭包核对后追加审计；验收和最终结项重新核对输入。原报告、中断、审查、null 退出码不改写。已有独立 PASS 可只重试插件门禁。不会运行模型或测试；不恢复跨 Leader 控制，不从复杂 source/动态重定向脚本猜子命令，不将本轮 BLOCKED 改成 PASS。旧数据保持兼容，新回执要求 0.30.0 写入版本。安装和驻留连接版本分别验证。

## 0.31.0 团队流程系统修复

统一当前合同与后续检查归属：普通审核、显式验收与历史原生登记共用范围规则；执行任务可保留有明确后续合同的 NOT_RUN 说明，不将当前失败或缺失检查放行。旧审核 PASS 的登记失败可通过 reconcile_team_review 预览并原位补登记，保留报告、检查、拒绝与中断历史，避免无意义的二次审核。

命令验证使用最后一次匹配的宿主结果，当前失败/未知不能被历史成功覆盖；阶段复用核对工作目录。停止期间登记不恢复执行状态；保存审核恢复要求原控制已恢复。批量推进返回真实部分成功与异常，失败的 terminal 交付缓存具体原因，不反复自动接收；原失败记录保留。场景回归覆盖正常执行、异常和恢复路径；真实业务核对记录仅保存在本地。

## 0.31.1 跨平台发布修复

验证目录按原生路径自身的 POSIX、Windows 盘符或 UNC 语法解析，避免服务器系统改变历史目录身份；不同盘符、共享目录与未知盘符相对路径不匹配。Windows 的 POSIX 命令准备仍明确提示使用原生命令输出预算和日志选项。补充路径与平台回归，面板验证原证据时间不被改写，事件等待测试留出持久保存时间。

## 0.32.0 初始化证据关联与等待成本

环境初始化链支持显式绑定到当前合同命令：核对原报告完整声明、原生 commandId、工作目录、真实成功退出码和未变输入，保留中断及审查原文。仅支持字面量初始化与 && 链，失败屏蔽、管道、动态命令和不透明脚本仍不能满足验收。旧准备记录缺少预执行指纹时明确提示使用原报告 manifest，不补造历史证明；manifest 全部文件哈希仍核对，输入根按原声明的源码/配置范围选择。

等待增加跨调用 waitCursor 和可直接复用的 continuationArgs，普通进度不触发状态/schema 重读；默认等待55秒，协调调用设置 functions.exec yield_time_ms=60000，减少中途返回的模型往返。阶段交接建议提前至60000当前输入 token 或30次命令，仍只在明确完成边界交接，不强制清空、降档或重跑。插件不能消除宿主有界等待产生的全部空闲模型轮次。

## 0.32.1 初始确认接续

初始用户点击“确认并开始”时，在保存本版本批准后通过标准 ui/message 发出一次用户启动指令，接续当前原 Leader；无需手动再回复启动。服务器核对当前项目、面板批准、version/hash、活动控制及未开工状态，消息只带绑定标识，不把任务文本插入指令。重复、多面板、刷新和 unknown 回执不重发；只有明确 failed 后允许用户手动重试。Leader 仍须核对保存的授权、控制和实际状态后拆分/派发，不能以消息正文替代审批或宣称执行。

这不是后台协调通道：进度、内部通知、停止/恢复与扩展确认仍使用原生内部协作和现有事件等待。没有 host message 能力时明确保留待接续。受控浏览器覆盖初始确认到规划和首批预留、刷新竞争、拒绝重试与未知回执；不代表真实 Desktop 已启动成员。原团队/计划记录没有迁移。
